# Dynamic Programming 1D

## 🎯 The Core Idea

Ever found yourself recalculating the same thing over and over? That's **recursion without memory**. DP is just **recursion with a notebook** — write down what you've computed so you never compute it twice.

**> Quick thought**: How many ways to climb 3 stairs if you can take 1 or 2 steps at a time?

<details>
<summary>Click to think about it...</summary>

To reach step 3, you could have come from:
- Step 2 (take 1 step)
- Step 1 (take 2 steps)

So ways(3) = ways(2) + ways(1)
</details>

---

## 🧠 How It Works (The "Aha!" Moment)

```
Stairs problem visualized:

Step 0 → Step 1 → Step 2 → Step 3
  1        1        2        3

Each step = sum of previous two steps (Fibonacci!)
```

**The secret**: Every problem builds on **smaller versions of itself**. If you know the answer for smaller inputs, you can build up to the big answer.

---

## 📝 The DP Framework

Ask yourself these 5 questions:

### 1️⃣ What's the state?
**> What information do I need to track?**

- Climbing stairs: `dp[i]` = ways to reach step `i`
- House robber: `dp[i]` = max money from first `i` houses
- Coin change: `dp[i]` = min coins for amount `i`

### 2️⃣ What's the recurrence?
**> How do I build dp[i] from previous states?**

```go
// Climbing stairs: I can come from i-1 or i-2
dp[i] = dp[i-1] + dp[i-2]

// House robber: Should I rob this house or skip it?
dp[i] = max(dp[i-1], dp[i-2] + nums[i])

// Coin change: Try each coin, take minimum
dp[i] = min(dp[i], dp[i-coin] + 1)
```

### 3️⃣ What's the base case?
**> What's the simplest case I know instantly?**

```go
dp[0] = 1  // One way to stay on ground
dp[1] = 1  // One way to reach first step
```

### 4️⃣ What's the iteration order?
**> Which direction do I fill the table?**

```go
// Forward: Each state depends on previous
for i := 2; i <= n; i++ {
    dp[i] = dp[i-1] + dp[i-2]
}

// Backward: Sometimes you need to go reverse
for i := n-1; i >= 0; i-- {
    // Process...
}
```

### 5️⃣ What's the answer?
**> Which dp cell holds the final answer?**

```go
return dp[n]  // Usually the last cell
```

## 🔥 Common Patterns (With Intuition)

### Pattern 1: "Pick or Skip" Decisions
**> At each step, I have a choice. What's better?**

**Example**: House Robber
```go
// At each house, I decide:
dp[i] = max(
    dp[i-1],              // Skip this house
    dp[i-2] + nums[i]     // Rob this house (can't rob previous)
)
```

**Think**: "If I take this, what must I give up?"

---

### Pattern 2: "Ways to Reach" Problems
**> How many paths lead here?**

**Example**: Climbing Stairs
```go
// I can arrive from either previous step
dp[i] = dp[i-1] + dp[i-2]
```

**Think**: "Where could I have come from?"

---

### Pattern 3: "Can I Reach?" Problems
**> Is this state achievable?**

**Example**: Jump Game
```go
dp[i] = true if any previous position can reach me
for j := 0; j < i; j++ {
    if dp[j] && j + nums[j] >= i {
        dp[i] = true
        break
    }
}
```

---

### Pattern 4: "Min/Max to Achieve" Problems
**> What's the minimum/maximum cost to get here?**

**Example**: Coin Change (min coins)
```go
dp[i] = infinity initially
for coin := range coins {
    if coin <= i {
        dp[i] = min(dp[i], dp[i-coin] + 1)
    }
}
```

**Think**: "Try all ways to get here, pick the best."

## 💡 Space Optimization Trick

**> Notice anything about dp[i]?**

Most of the time, you only need the last 2-3 values:

```go
// Before: O(n) space
dp := make([]int, n+1)

// After: O(1) space!
prev2, prev1 := 1, 1  // dp[0], dp[1]
for i := 2; i <= n; i++ {
    curr := prev1 + prev2
    prev2 = prev1
    prev1 = curr
}
return prev1
```

**When can you optimize?** When dp[i] only depends on the last k states.

## ⚠️ Common Pitfalls (Don't Fall For These!)

1. **Wrong base case**: Always test with n=0, n=1 manually
2. **Integer overflow**: Use `int64` for large results, or mod operation
3. **Off-by-one**: `dp[i]` vs `dp[i-1]` — trace through small example
4. **Uninitialized values**: Set to -1 or infinity when computing min/max

---

## 🚀 When to Use DP

✅ **Use DP when:**
- Problem asks for "number of ways"
- Problem asks for "minimum/maximum" to achieve something
- You see overlapping subproblems (same inputs computed repeatedly)
- Problem can be broken into smaller versions of itself

❌ **Don't use DP when:**
- Input size is huge (like 10^9) — need math formula instead
- Problem requires all permutations (backtracking instead)
- Greedy choice works (local optimal = global optimal)

## 📊 Complexity

| Aspect | Cost |
|--------|------|
| Time | O(n × states) — usually O(n) for 1D |
| Space | O(n) → can optimize to O(1) often |
